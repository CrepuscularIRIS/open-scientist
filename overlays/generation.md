# Open Scientist overlay for RS Phase 2.1 + 2.2 (ideate_select + ideate_generate)

Read this together with the RS prompts. Where they conflict, THIS file wins.

1. **Gap order is fixed.** `phase1/soundness_gaps.json` → `order` lists the gaps that passed the independent soundness verifier, mainline first. Choose the anchor gap from the FIRST entry whose `mainline_relation` is `target`; pick a later one only if the first is structurally unusable, and say why in `selection_rationale`. Gaps that were killed are not in the list, so never revive them. Lite mode has no gap verifier: use the gaps of `phase1/phase1_output.json` in their order, `mainline_relation=target` first.
2. **Classical construction (the solution-side core).** `phase1/classical_anchors.json` → `order` lists classical anchors modeled to the user's Q1–Q8 standard (original problem → construction → preserved property and its conditions → mapping with mismatch). Use the FIRST anchor of the chosen gap (a later one only if the first cannot be realised on this code — say why). The candidate's mechanism must be that anchor's `construction` transported to `entry`, and must state: which `property` it keeps, which `conditions` hold here and which are replaced by a proxy (and what the proxy breaks first), and the anchor's `mismatch`. Cite the anchor (authors, year, venue). Do not add mechanism components that the construction does not need. **Division of labour (user 2026-11-09):** the anchor decides WHAT (construction + preserved property); the RS pattern and sub_pattern keep their normal role and decide HOW it lands — choose them by the RS rules as usual (sibling/companion contracts, no quota) and use the sub_pattern's tactic as the implementation recipe. One added constraint: the chosen pattern / sub_pattern must not contradict the anchor's construction or break its conditions; if none fits without contradiction, use `sub_pattern: null` and say why.
3. **Intervention object.** `intervention_object` must name the concrete code object the method changes (module / function / input / loss term). The card-level soundness verifier reads it against the code.
3b. **Intervention locus (2026-11-11).** Read `phase0/causal_order.json` `edges`. If the candidate's `intervention_object` acts downstream of a constraint that the audit placed upstream of the target (e.g. a reward / objective change while the actor cannot observe the quantity the reward asks it to correct), the candidate must either act on that upstream constraint, or add a field `upstream_not_binding` with a one-paragraph argument (cite the edge and the counterfactual) why that constraint does not cap this mechanism. Without it, choose another anchor. A user direction ("try kernel X vs kernel Y") does not override this rule; record the conflict in `user_direction_disposition`.
4. **Keep the claim minimal.** State the mechanism on the target bottleneck itself. Do not widen it to a class of problems unless that changes the experiment.
5. **Overlap with existing work is allowed; differentiation is not a goal; no forced scoop check (user 2026-11-08, 2026-11-13).** This is an integration / application paper. The following RS rules are OVERRIDDEN here: `ideate_generate` Hard rule 2 ("no regression to an ancestral node"), the instruction that the mechanism "must NOT reduce to an ancestral/occupied node", the "occupied-source constraint" that Phase 2.1 records in `selection_rationale`, and the requirement that the candidate be "substantively novel relative to closest_adjacent". Phase 2.1 must NOT write an occupied-source exclusion list; if `method_lineage` flags a family as occupied, that only names what to cite and compare against. A family already used by the literature or by a community switch (data-distribution fixes, noise calibration, domain randomisation, ...) is admissible and is PREFERRED when it is the best fit for the residual gap. Collision / novelty findings (RS 3.x, scoop checks) are advisory: they never change the mechanism or drop a candidate.
5b. **Order of reasoning; no technique bound in advance (user 2026-11-13).** Work in this order and show it in the candidate: (i) the measured phenomenon and the causal link that most limits learning (from Phase 1 + admission); (ii) `why_existing_insufficient` — for each existing mechanism or switch in `prior_sweep.json` that touches the target, one sentence on what key information / gradient path / state coverage it still fails to supply, grounded in the sweep result, not in an argument; (iii) only then the mechanism: the SIMPLEST training-side change inside the baseline framework that supplies that missing information. Do not start from a technique (a named method, a loss family, an architecture) and look for a place to use it; a user or host hint naming a technique is recorded in `user_direction_disposition` and does not bypass (i)–(ii). Prefer fewer new components, fewer hyper-parameters and no deployment change.
6. **Baseline and residual (0.10).** Read `phase1/prior_sweep.json`. Existing switches have already been run in `regime`; the candidate is designed for `residual_gap`, not for the whole target. Set `baseline_switch` = `best_deployable`; the falsification experiment compares against that switch in the same `regime`, not against the unmodified baseline. Prefer the lowest rung that can close the residual and say in `selection_rationale` why the rungs below it cannot: (a) parameterise or extend the working switch, (b) integrate a known technique on top of it, (c) a new construction. If the anchor's construction coincides with an existing switch, the candidate is "that switch + what the residual needs" — never a different mechanism chosen in order to differ. `hook`, `hook_shape_rationale` and `differentiation_from_lit` must not list "does not change what the existing switch changes" as an advantage.
7. **Deployment contract (0.10).** Read `<project>/.open-scientist/deploy_contract.md`. Fill `deploy_inputs` — every quantity the deployed policy / estimator reads, its on-board source, and the code object that provides it — and `train_only_signals` (privileged quantities used only in training). If any deploy-time input is outside the contract, set `role: "upper_bound"`: such a candidate may be run as a control arm but is never the method and never a contribution, whatever it scores. Do not hide a contract violation behind an "estimator" unless the estimator's inputs are themselves in the contract and it is part of the candidate.
8. **Engagement and degenerate solutions (0.10).** Add `engagement_metric`: the intermediate quantity that must change in the REAL system (not only inside the model / imagination) if the mechanism works, and how to measure it from a rollout dump. Add `degenerate_solutions`: the cheapest ways the added loss / reward / constraint could be minimised without the intended behaviour (standing still, relying on training-only noise, early termination, ...), and what in the objective blocks each. The pre-review scores this (S8) and failure attribution uses the engagement metric.
9. **Slate of two (0.10; when the host says a sibling candidate exists).** If `phase0/sibling_candidate.json` is among the inputs, this run is the SECOND arm of a two-arm slate on the same target (one arm per GPU, trained in parallel, no repeated seeds). The second candidate must differ from the sibling in kind, not in a constant: a different classical anchor (the next entry of `classical_anchors.json` → `order`) or, with one anchor, a different `intervention_object`; and a different causal premise, so that the two can fail for different reasons (state both premises in `selection_rationale`). Same target, same `baseline_switch`, same `regime`. If no second mechanism of a different kind is defensible, say so in a top-level `no_second_candidate` field instead of producing a variant — the host will use the second GPU for the first candidate's decisive control arm.
